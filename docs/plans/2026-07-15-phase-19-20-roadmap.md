### 需求 3：Gateway Overhead 评估

发现了一个严重偏差。`proxy_server_request` 在 litellm 中的实际用途与我最初理解的不同：

**litellm 的 `proxy_server_request` 定义** (`litellm_pre_call_utils.py:1350`)：
```json
{
  "url": "<请求 URL>",
  "method": "POST",
  "headers": "<请求头快照>",
  "body": "<请求体快照（去敏感字段后）>",
  "arrival_time": 1712345678.123
}
```

**核心用途**：
| 用途 | litellm 源码位置 |
|------|------------------|
| **Queue Time 计算** | `common_request_processing.py:1068-1075`：`queue_time = processing_start_time - arrival_time` |
| **UI Drawer 请求展示** | `usage_endpoints.py:498-502`：`proxy_server_request.body` 作为 request input 展示 |
| **Header 透传** | guardrails 用 `proxy_server_request.headers` 获取原始请求头 |

**aigw 现状**：
| 项目 | 状态 |
|------|------|
| `proxy_server_request` 字段 | ❌ schema 定义存在（BLOB），代码始终写入 `None` |
| `request_duration_ms` | ✅ 有总耗时，但无法拆分 |
| `ttft_ms` | ✅ 有（streaming 场景） |
| `queue_time` / `arrival_time` | ❌ 未记录 |
| Overhead 拆分 | ❌ 无法评估「网关处理」vs「上游响应」占比 |

**关键区别**：我之前规划 Stage 58 把 `proxy_server_request` 当成 upstream timing 记录，但 litellm 实际上是**请求入口审计快照**。需要同时做两件事：
- a) 请求入口时写入 `proxy_server_request`（对齐 litellm：url/method/headers/arrival_time/body）
- b) 额外记录上游发送时间戳（可以放在一个新字段或 `proxy_server_request` 的扩展中）

✅ 已确认：ms 级别精度

### 新发现 Bug：SpendLog 中的 model_group/custom_llm_provider 缺失

| 字段 | 当前写入 | 应该写入 |
|------|---------|---------|
| `model` | ✅ `model_name`（正确的代理模型名） | — |
| `model_id` | ❌ 始终 `None` | proxy_models 的 model_id (UUID) |
| `model_group` | ❌ 始终 `None` | litellm_params 中的 model 字段（上游模型名，如 `gpt-4`）|
| `custom_llm_provider` | ❌ 始终 `None` | litellm_params 中的 custom_llm_provider（如 `openai`）|
| `api_base` | ✅ 正确填入 | — |

**根因**：`chat.rs` 和 `v1_messages.rs` 中所有 4 个创建 SpendLog 的地方都写了 `model_id: None, model_group: None, custom_llm_provider: None`。但 resolve 阶段已经从 proxy_models 查到了 model_id 和 litellm_params，只是没写入 SpendLog。

这在 Spend Logs 页面表现为：model 列显示代理模型名（正常），但无法展示上游模型组和 provider 信息。

**结论**：需要把 resolve 时的 `ProxyModel.model_id` 和 `litellm_params.model`/`custom_llm_provider` 写入 SpendLog。这会影响 Model 过滤器的准确性。

### 新发现：Token 计费逻辑分析

**计费公式** (`chat.rs:58-61`)：
```rust
pub(crate) fn calc_spend(prompt_tokens, completion_tokens, input_cost, output_cost) -> f64 {
    prompt_tokens * input_cost.unwrap_or(0.0) + completion_tokens * output_cost.unwrap_or(0.0)
}
```

**定价来源**（`resolver.rs:282-288`）：从 `model_info.input_cost_per_token` / `output_cost_per_token` 读取。

**测试数据中的定价值**（`resolver.rs:342`）：
```json
{"input_cost_per_token": 0.00003, "output_cost_per_token": 0.00006}
```
即 $30/M input, $60/M output → GPT-4 价格，逻辑正确。

**前端展示**（`models/index.tsx:86-93`）：`input_cost_per_token * 1_000_000` → 显示为 $30/M。✅ 正确。

**潜在风险**：如果用户错误地将「每百万 token 单价」（如 30 而非 0.00003）填入 `input_cost_per_token`，会导致 spend 严重偏高。这是配置问题，不需要代码修正。

**✅ 结论**：计费逻辑本身正确，无 bug。`input_cost_per_token` / `output_cost_per_token` 应填入**每 token**（而非每百万）的 USD 价格。

### Stage 58：Gateway Overhead 评估与展示（对齐 litellm proxy_server_request）

**预估**: 7-8h | **类型**: 后端 + 前端 + BDD 测试

**现状**：`proxy_server_request` 始终为 None。无 arrival_time / queue_time / overhead 拆分。

#### 任务清单

**后端部分**：

1. **请求入口写入 proxy_server_request**（对齐 litellm，在 handler 而非 adapter 层）
   - 坐标：`chat.rs` / `v1_messages.rs` 中创建 SpendLog 之前
   - 写入内容：
     ```json
     {
       "url": "/v1/chat/completions（或 /v1/messages）",
       "method": "POST",
       "headers": {"user-agent": "…", "x-forwarded-for": "…", …} ,
       "body": <请求体快照>,
       "arrival_time": <SystemTime.now()>
     }
     ```
   - 注意：`body` 是否存储有争议 — 请求体已有 `messages` 字段，避免重复。建议存 `{}` 占位。

2. **Queue Time 计算**（对齐 litellm）
   - 在请求被 handler 开始处理时记录 `processing_start_time`（即 `let start_time = Utc::now()`）
   - `queue_time_ms = processing_start_time - proxy_server_request.arrival_time`
   - 这是 tokio 调度延迟（从接收请求到开始处理之间的排队时间），通常接近 0

3. **Overhead 时间拆分**
   - 在 adapter 发送请求之前记录 `upstream_sent_at`（system time）
   - 在收到 upstream 首字节时记录 `upstream_first_byte_at`
   - 在收到 upstream 完整响应时记录 `upstream_ended_at`
   - 写入一个单独 JSON（可放在 `proxy_server_request` 扩展字段或新字段 `upstream_timing`）：
     ```json
     {
       "upstream_sent_at": "…",
       "upstream_first_byte_at": "…",
       "upstream_ended_at": "…",
       "upstream_status": 200
     }
     ```
   - 计算公式：
     - `gateway_overhead_ms = request_duration_ms - upstream_duration_ms`
     - `upstream_duration_ms = upstream_ended_at - upstream_sent_at`
     - `ttft_ms = upstream_first_byte_at - upstream_sent_at`（与已有 ttft 交叉验证）

4. **DB 更新** (`db.rs`)
   - `update_spend_log()` 增加 `proxy_server_request` 参数
   - 或在 `insert_spend_log` 时就写入

5. **API 响应中返回 overhead 计算字段**
   - `spend.rs` 的 json! 宏中增加：
     - `proxy_server_request`（已有）
     - `gateway_overhead_ms`（计算得出）
     - `queue_time_ms`（计算得出）

**前端部分**：

6. **Overhead 展示**（DetailDrawer 新增 Timing Breakdown 区域）
   - 显示：
     - Queue Time: Xms（请求排队）
     - Gateway Processing: Xms（网关处理）
     - Upstream Roundtrip: Xms（上游响应）
     - Total: Xms = Queue + Gateway + Upstream
   - 水平 bar 可视化各部分占比
   - 旧日志（无 proxy_server_request 数据）→ 显示 "Timing breakdown not available for this request"

7. **BDD 测试**
   - 验证新请求有 proxy_server_request 数据
   - 验证 queue_time / gateway_overhead 计算正确
   - 验证前端显示 timing breakdown

8. **验收标准**
   - 新请求记录 `proxy_server_request`（含 arrival_time）
   - `upstream_timing` 或等价字段记录上下游时间拆分
   - 前端展示 timing breakdown（queue + gateway + upstream）
   - 旧日志优雅降级（无 breakdown 数据时不报错）
   - BDD + UT 通过
